When a browser reads text aloud with speech synthesis, nothing on the page shows which word is being spoken. speechType listens to the Web Speech API’s boundary events and marks each word as it is spoken: by default with weight, optical size and spacing on a plain span around each word, or (next release) with a highlight that adds nothing to the page. The text stays real text either way: links keep their names, and the accessibility tree keeps the paragraph you wrote.

Every word spoken carries its own weight, a breath of meaning that arrives, lingers, and fades. To read aloud is to make language visible in time, each syllable a footprint left in the air. The voice knows where it is. The page does not.

Press Speak to hear the paragraph read aloud by your browser’s speech synthesis, with each word marked as it is spoken, or use the Word slider to step through by hand. “read aloud” is a real link: it stays a link, with its name, in both modes. Meant for read-along reading aids, language learning and teleprompters. It is not a screen reader and doesn’t replace one.

WHAT SPLITTING TEXT COSTS — MEASURED ON THIS PAGE

speechType has to put every word in its own span, and so does any effect that moves words or letters one at a time. Until version 1.1.0 it also hid those spans from screen readers, a mistake several of our tools made. Below, one sentence with a link is set three ways: as written, split by a published library (the real package, run in your browser), and wrapped in place the way speechType does it now. Each version reports its measured width and what it offers assistive technology.

The words used here. A screen reader reads a page aloud for someone who can’t see it. It doesn’t read the pixels: it reads the accessibility tree, the browser’s own list of what is on the page. In that list each thing has a role (paragraph, link, heading) and may have a name (for a link, its words). A tab stop is a place the Tab key lands. aria-hidden removes something from that list; aria-label gives something a name by hand. An inline-block is a piece of text made into its own small box, which is what lets an animation move it. Kerning is the font tucking certain pairs of letters closer (A and V); a ligature is two or three letters drawn as one joined shape (ffi). Both happen only between letters that are set together.

How to read this. Roles, names, tab stops and text objects are computed in your browser from the live markup, following the accessible-name rules (AccName 1.2). They describe what the page offers assistive technology, not what any screen reader says. We checked every reading against Chrome’s own accessibility tree across the presets and settings; the counts are in the paper’s method section. One known difference: Chrome stops building a name from content after 100 objects, so a heading split into inline-block characters (the first preset is long enough) gets a shorter name in Chrome than the full one shown here. Widths are measured from the rendered lines, so they change with your browser, zoom and fonts.

More pieces is not the same as broken. Wrapped in place, the words are all still there and the names are right, but the text now sits in many small objects. Chrome reports them one after another on the same line. Whether a screen reader runs them together is something this page can’t tell: a 2018 report from a VoiceOver user found iOS stopping at each inline element inside a link. The rows that hand over the sentence in its original pieces are the unsplit one, anime.js’s hidden copy and “boxes beside the real text”.

Limits. One font and one line. What splitting into letters costs depends on the text: an ordinary English sentence here gains about 1 to 2%, the line built from kerning pairs about 6%, the Arabic phrase about a third (its letters stop joining), and SplitType cuts the Devanagari word into parts. Splitting by words costs almost no width in any of these libraries, though GSAP’s link still loses its name. A plain inline span keeps the shaping only while the pieces share one style: change a piece’s weight or size and the browser shapes it separately, and the line changes width. Motion+ splitText is a paid product and isn’t run here; the paper reports what its published build did.

HOW IT WORKS

The audio-text gap

When the browser speaks text via SpeechSynthesisUtterance, words are heard but not seen. There is no CSS property that tracks synthesis progress — the visual and the auditory are decoupled by design. speechType closes that gap.

Boundary events drive emphasis

The Web Speech API fires boundary events as each word begins. speechType maps the reported character index to the word and applies typographic emphasis (wider tracking, heavier weight, larger optical size) while dimming the other words. Not every voice sends word boundaries; with one that doesn't, the text is spoken and nothing is marked.

Imperative for performance

During active speech, startSpeechType handles each boundary event directly — updating span styles without touching React state or triggering re-renders. The boundary event fires, the span style changes, and the frame is painted. No scheduling, no batching delay.

React or vanilla JS

SpeechTypeText and useSpeechType manage span preparation and React-driven emphasis. startSpeechType is the vanilla JS entry point — it wraps, speaks, and syncs, returning a stop function.

USAGE

TypeScript + React · Vanilla JS

Drop-in component

import { SpeechTypeText, startSpeechType } from '@overpunch/speechtype'
import { useRef, useState } from 'react'

// Drive activeWordIndex via startSpeechType or your own state
const [activeWordIndex, setActiveWordIndex] = useState(-1)
const ref = useRef<HTMLParagraphElement>(null)

// startSpeechType updates the spans imperatively during speech:
<SpeechTypeText ref={ref} activeWordIndex={activeWordIndex}>
  The voice knows where it is. The page does not.
</SpeechTypeText>

Start speech synthesis and sync emphasis

import { startSpeechType } from '@overpunch/speechtype'

const el = document.querySelector('p')
const stop = startSpeechType(el, { rate: 0.9, activeWeight: 700 })

// Later — cancel speech and restore styles:
// stop()

Hook — manual control with your own active index

import { useSpeechType } from '@overpunch/speechtype'
import { useRef } from 'react'

// Inside a React component:
const ref = useRef(null)
useSpeechType(ref, activeWordIndex, { inactiveOpacity: 0.4 })
return <p ref={ref}>Every word spoken carries its own weight.</p>

Options

Option	Default	Description
activeTracking	0.06	Letter-spacing on the active word in em.
activeWeight	+300	wght axis value on the active word. Unset: the word's own weight plus 300 (400 becomes 700).
activeOpsz	×1.5	opsz axis value on the active word. Unset: 1.5 times the word's own optical size.

LIMITS
We have not tested speechType with a screen reader. What we checked is Chrome's accessibility tree, where names and roles match the unwrapped text. A span per word does split the text into more pieces in that tree, and a 2018 report found VoiceOver on iOS stopping at inline elements; the highlight mode avoids spans altogether.
The default emphasis makes the spoken word heavier and wider, so lines can rewrap while it plays. The highlight mode can't move text, and can't change weight or size either.
Dimming the other words lowers their contrast for as long as a word is active. The published default, 0.45, puts black-on-white text at 3.4:1, under the 4.5:1 that WCAG AA asks; the next release defaults to 0.6 (5.7:1). On softer colours you need more: the demo above shows the ratio for this page. Set inactiveOpacity to 1 for no dimming.
Speech synthesis, its voices and its word-boundary events come from the browser and the operating system, and differ between them.
